# Session 2026-08-31: Stale Rankings — Zhao Xintong Not Showing as World #1

## Symptom
User reported `RankingEnhanced.tsx` showing Judd Trump #1 in the app's rankings, when Zhao Xintong had become the real-world snooker #1 on 2026-08-27 after the Wuhan Open (confirmed via [SnookerHQ](https://snookerhq.com/2026/08/27/zhao-xintong-world-number-one-snooker/)). Asked to check our DB against the live snooker.org API.

## Root cause chain
1. `RankingEnhanced.tsx` renders exactly what the backend serves — not a frontend bug. Production `/oneFourSeven/ranking-types/MoneyRankings/` was itself returning stale data (Trump #1, Xintong #3) when checked directly via curl.
2. `auto_live_monitor.py` (the 24/7 Railway "auto command" daemon) is the only thing that refreshes rankings automatically, via `_check_tournament_end_updates()` → `update_rankings` management command.
3. That call was placed **only inside the idle-only `else` branch** of the main loop's `if has_active_matches / else` (old line 146, inside the `else` at old line 127).
4. `_has_active_matches()` returns `True` if **any** `Event` (main tournament *or* Qualifiers) has `StartDate <= today <= EndDate`. Qualifiers for some tournament run almost continuously through the season, so this is essentially always `True` — the idle branch, and the ranking refresh gated inside it, almost never runs in practice, despite the command's own docstring calling "tournament end detection" a core feature.
5. Wuhan Open ended 2026-08-29. Confirmed via Railway logs (`mcp__railway__get-logs` on the "auto command" service, filtered for `RANKING`, `TOUR_END`, `Wuhan` from 2026-08-25 onward): **zero matching log lines** — proving `_run_tournament_end_updates` never fired for it in the 2+ days since it ended.

## Files touched
- `maxBreak/oneFourSeven/management/commands/auto_live_monitor.py` — moved the `_check_tournament_end_updates()` call out of the idle-only `else` branch to run unconditionally every loop tick, before the active/idle branch split. One-line-relocation fix; the function itself (`_check_tournament_end_updates`, `_run_tournament_end_updates`, `_has_active_matches`) was NOT changed — it already had correct dedup (`processed_tournament_ends`) and a 48h detection window, it just wasn't being called often enough.
- `maxBreak/oneFourSeven/tests_tournament_end_ranking_gate.py` (new) — 10 assertions:
  - 3 wiring-regression tests (`TournamentEndCheckRunsEveryTickTestCase`): runs while `has_active_matches=True`, runs while `False`, runs *before* `_run_live_updates()` in the active branch. **Verified these actually catch the bug** — reverted the fix locally, re-ran: 2 of the 3 failed exactly as predicted (`_check_tournament_end_updates` called 0 times while active). Restored the fix, all pass.
  - 7 detection/dedup tests (`CheckTournamentEndUpdatesDetectionTestCase`) against `_check_tournament_end_updates()` itself: no ended tournaments, the real Wuhan-Open-shaped scenario, >48h-old exclusion, no-finished-matches-yet skip, already-processed dedup, multiple concurrent tournament ends, stale-processed-ID (>7 days) cleanup.

## Verified
- Full `oneFourSeven` test suite (`tests`, `tests_favorite_id_churn`, `tests_player_stats_targeting`, `tests_tournament_path`, plus the new file): **156 tests, 1 pre-existing failure** (`PlayerMatchHistoryOrderingTest.test_null_date_appears_last`, already logged as Open Mission #1 in `docs/OPEN_MISSIONS.md` — confirmed unrelated, untouched by this change). No new regressions.
- Production API re-checked live after a manual `update_rankings --ranking-type all` run (see below): `MoneyRankings` and `MoneySeedings` both now show Zhao Xintong #1 (£1,253,550) ahead of Neil Robertson (£1,198,200), matching real-world news.
- Committed `7d9f81e3` and pushed to `master` — Railway auto-deploys on push (per this repo's standard flow) to both the `web` and `auto command` (live-monitor) services.

## Lessons for future agents
- **`_has_active_matches()` is a poor gate for "is anything worth doing right now" logic** — it's `True` almost all the time once Qualifiers events are considered, not just during a main tournament. Any future automation gated behind `if has_active_matches / else` should be checked against this same trap: does it actually need to wait for "idle", or does it just need dedup (like `processed_tournament_ends` already provides here)?
- Production Postgres is reachable directly from a local `venv` via the `DATABASE_URL` in `maxBreak/.env` (proxied through `metro.proxy.rlwy.net`) — existing management commands (e.g. `update_rankings`) can be run locally against production directly for one-off manual fixes/backfills, no Railway shell/exec needed. Confirm this is still the case before reusing — a rotated DB password would break it silently (see the `.env`'s own "3. Update DATABASE_URL above with new password" comment).
- Railway MCP (`mcp__railway__get-logs`, `list-services`) is the fastest way to get real evidence of whether a scheduled/daemon job actually ran, rather than reasoning from source code alone — the "auto command" service ID and production environment ID for this project are in this doc's git history if needed again (Max Break project `584486f6-272b-4c3d-b78b-c9dc3bd932c0`, "auto command" service `bdc04612-10ec-4f5f-9e40-033767e6fd15`, production env `22b95876-c730-4332-9908-190dd4f4c54f`).
- Testing `auto_live_monitor.py`'s `handle()` end-to-end is expensive/slow because `_startup_sync()` and the boot-time `_has_active_matches()` check both do real work before the main loop starts — any test exercising `handle()` must stub `_startup_sync` and set an explicit `side_effect` list on `_has_active_matches` (boot call + loop call are the same mocked method, called twice) rather than a flat `return_value`, or the boot-time preamble contaminates loop-body assertions (see `test_ordering_tournament_end_before_live_updates` in the new test file for the pattern).
